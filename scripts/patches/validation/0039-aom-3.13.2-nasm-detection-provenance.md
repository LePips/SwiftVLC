## Observed failure and root cause

The first clean all-platform build at SwiftVLC revision
`360bd70fc3423b984fce21045bd8c499fe5d7874` completed the iOS, tvOS,
visionOS, and macOS arm64 builds before failing while configuring the macOS
x86_64 libaom 3.13.1 contrib. CMake reported:

```text
Unsupported nasm: multipass optimization not supported.
```

This was a false capability result, not a compiler crash or an intermittent
download failure. NASM 3 split command help into topics. The pinned NASM 3.02
binary and SwiftVLC's transparent wrapper therefore report:

- `nasm -hO`: optimization help containing `-Ox`;
- `nasm -hf`: object formats containing `macho64`, but no `-Ox`.

libaom 3.13.1 queried only `-hf` and expected both capabilities in that one
response. AOM fixed the defect by querying `-hO` for optimization and `-hf`
for object formats in
[`6d2b7f71b98bfa28e372b1f2d85f137280bdb3de`](https://aomedia.googlesource.com/aom/+/6d2b7f71b98bfa28e372b1f2d85f137280bdb3de),
then included the fix in 3.13.2. NASM documents the 3.0 help-topic change in
its [3.x version history](https://www.nasm.us/doc/nasmac.html#section-C.1.3).

The defect surfaced only at macOS x86_64 because that was the first completed
matrix target that configured libaom's x86 NASM sources. Earlier arm64 targets
do not exercise this path, so their success could not validate x86 assembler
consumer compatibility.

## Why the VLC 3.13.2 update is used

An exact backport of AOM's four-line CMake change also fixes the immediate
failure. Mirroring VLC's official 3.13.2 update is preferable for the release
stack because it removes a long-lived private nested patch, uses the first
official VLC dependency update that incorporated this fix, and keeps the
dependency checksum identical to that audited VLC recipe. VLC master has since
advanced to libaom 3.15.0; 3.13.2 is intentionally the minimal ABI-compatible
step from this branch's pinned 3.13.1 rather than a multi-release dependency
jump. The release also contains several encoder memory-safety fixes; SwiftVLC's
current contrib configuration disables the AOM encoder, so the relevant
compiled behavior change is primarily the build-system and decoder-side
maintenance update.

## Source and behavior policy

1. `contrib/src/aom/rules.mak` must contain exactly one
   `AOM_VERSION := 3.13.2` assignment and the official Google Storage release
   URL used by VLC.
2. `contrib/src/aom/SHA512SUMS` must contain only the audited 3.13.2 archive
   line. An old version, old filename, alternate URL, or one-byte checksum
   change fails the source contract.
3. Patch 0039 owns exactly those two existing VLC paths. Renames, added files,
   deleted files, binary payloads, or an extra diff section are rejected.
4. The CMake behavior probe contains libaom 3.13.2's `test_nasm` function and
   runs it against a fake NASM 3 help surface. The working case must call
   `-hO` and then `-hf`; missing optimization and missing Mach-O format cases
   must fail with their specific diagnostics.
5. A generated legacy probe changes the first query back to `-hf`. It must
   reproduce the 3.13.1 false rejection, proving that the regression test is
   sensitive to the actual failure rather than merely checking a version
   string.

## Executed evidence

- Patch 0039 applies after the frozen 0038 patch and reverse-applies cleanly
  from the resulting two-file source state.
- The standalone source checker passed two exact source paths, eight deliberate
  source/patch/probe mutations, and four executable CMake/NASM behavior cases.
- The local pinned NASM 3.02 binary and installed Apple wrapper both returned
  `-Ox` for `-hO` and `macho64` for `-hf`, with successful exit status.
- A targeted macOS x86_64 libaom 3.13.2 contrib configure/build used the exact
  Apple NASM wrapper environment from the failed matrix target. Configuration
  accepted the split probes, all 360 Ninja steps (including NASM objects)
  completed, and the static library installed successfully in 30.60 seconds.
  This retained-tree result is diagnostic evidence only and does not replace
  the clean all-platform rebuild.

## Release gate and residual risk

Patch 0039 changes native dependency bytes. A release candidate therefore
requires two clean, independent all-platform libVLC builds from the same final
SwiftVLC revision, byte-for-byte canonical artifact comparison, and the full
per-object Mach-O metadata/alignment validator. Existing output from the
failed 3.13.1 build cannot be resumed or promoted.

The physical-device qualification suite remains a separate gate for playback,
seeking, Picture in Picture, Cast, audio-session recovery, and lifecycle
behavior. This source contract deliberately proves the dependency selection
and the discovered NASM consumer failure; it does not claim runtime media
correctness.
